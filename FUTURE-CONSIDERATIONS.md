# Future Considerations / Standing Checklist

This is the working list of things that are known, logged, and deliberately not
acted on yet — either because they're not urgent, need more real-world usage
data first, or represent a bigger architectural step than the project needs
right now. Split out from `PROJECT-NOTES.md` once that document's own
checklist section got long enough to make the "how this works today" content
harder to find.

*(Also tracked separately in ongoing memory — this is the durable snapshot as
of this write-up.)*

- [ ] **Bulk-refreshing existing folders after a template/engine change doesn't scale** — currently means manually typing out every affected folder name into a Cowork prompt (or doing it by hand), split by person vs. property type. Fine at today's folder count; genuinely painful once the list is much longer. Worth a real fix eventually — e.g., a small script that auto-discovers every person/property folder by checking for a marker in each `data.json`, rather than requiring a hand-maintained list every time.
- [ ] **Photo storage/bandwidth headroom, once the project scales much further** — GitHub (soft-recommends staying under ~1-5GB total repo size) and Vercel Pro's 1TB/month included bandwidth both have real headroom today (roughly hundreds of fully-loaded people before either becomes a concern, at a realistic ~2MB/photo estimate), especially since Gallery photos already lazy-load rather than loading on every page view. Not a problem now — but if photos start arriving unoptimized (some phones produce 8MB+ JPEGs by default) or the person/property count grows well beyond current scale, that headroom shrinks faster than the current math assumes. If it ever becomes real: add a compression step before photos go into a folder, or move heavy media to a dedicated image host instead of the git repo. A "someday, if" item, not an active concern.
- [ ] **Overall hosting capacity — how many cards before this system needs rethinking** — checked Vercel's actual published limits rather than estimate: a single deployment allows up to 15,000 source files. At roughly 3-5 files per person/property folder (template copy, data.json, photos), that's a rough hard ceiling around 3,000-5,000 people — far beyond current scale. GitHub's soft size guidance (see the item above) lands in the same "hundreds to low thousands" range depending on photo usage. **The more realistic bottleneck is process, not hosting**: the bulk-refresh scalability problem (see that item elsewhere in this list) starts hurting in the dozens-to-hundreds range, and Boris's own manual intake pace (read submission, convert, load into generator.html, build, push) scales linearly with volume — that's very likely the first real constraint hit, well before any server-side number matters. Logged for reference; nothing to act on now.
- [ ] **Manual intake pace — flagged for further attention** — every new card currently depends on Boris personally: reading the submission, converting it (now via message-to-json.html), loading it into generator.html, building, and pushing. This scales linearly with request volume and is the most likely of everything on this list to become a real constraint first, since it doesn't wait for any technical threshold — it's felt the moment daily volume outpaces the time this takes. Claude Cowork (direct local file access, multi-step task handling) came up as a plausible path worth exploring for this, and separately for the bulk-refresh problem above, since both are fundamentally "do the same multi-step thing across many items" tasks — but this hasn't been tested against the real workflow yet. Worth a real look before volume forces the issue, not after.
- [ ] **Shared links show a generic "Contact" preview, not the person's name — low priority, nice-to-have** — when a card's URL is shared, the link preview (title, favicon) shows the plain word "Contact," since `<title>Contact</title>` is hardcoded in the shared template and there's no Open Graph data (`og:title`, etc.) at all. The page does set the name dynamically via JavaScript once loaded, but that doesn't help here — the app generating a link preview reads the raw HTML before any JavaScript runs, so it never sees it. Fixing this for real means each person's own copy of index.html would need a small, genuinely different title/meta tag baked in at creation time (generator.html could write this automatically) — a minor departure from every person's file being byte-for-byte identical, with a small knock-on effect on the bulk-refresh item above (a future engine update would need to preserve each person's name rather than overwrite it). Deliberately left alone for now — logged for possible future action, not an active concern.
- [ ] **A realtor-specific animated demo** — the existing animated-demo.html shows the generic tap-to-share flow (tap, card opens, save to contacts). It says nothing about the parts of the product that actually matter most to a realtor specifically — linked property listings, photo galleries, scheduling a showing. A version built around that flow would need genuinely new frames and content, not a copy-and-relabel of the existing demo. A real project of its own, not a quick add-on — logged here rather than built alongside the realtor pricing schedule and letter, which share existing content patterns and don't carry the same scope.
- [ ] **True aggregation of collected contacts, via a third-party form service — positioned as a paid add-on, not a base-tier feature.** The lighter fix (a "Where we met" field added to the existing Share Your Info text/email template) shipped directly. This is the bigger version: replacing that text/email handoff with an actual embedded form (something like a Google Form feeding a Sheet), so every contact a realtor collects lands automatically in one running, dated list instead of scattered one-off messages in their regular inbox — with real structure too, e.g. a buyer/neighbor/just-curious dropdown, rather than hoping a visitor thinks to type it into a blank line. Would genuinely solve the "stash of business cards to go through later" problem that came up repeatedly in research into realtor pain points.
  - **Why this is an add-on rather than something everyone gets**: this requires its own form and sheet *per realtor*, individually connected in their own `data.json` — not a one-time, project-wide setup. That's a real, recurring cost that lands on every future realtor-tier customer, not a cost paid once and forgotten. It also breaks the "one shared-file edit updates every card automatically" model this project has relied on for everything else — a field change, a lost Google account, or the service changing its embed method all require fixing that specific person's form individually, not one shared fix that propagates everywhere.
  - **The alternative — one shared form for all realtors** — would be a genuine one-time, project-wide setup, but shifts the cost elsewhere: either building a way to filter each realtor's own submissions out of a shared sheet (real ongoing technical work), or manually forwarding each person's contacts yourself, which puts Boris back in the manual-middleman role this was meant to remove.
  - **Also a real, categorical privacy change worth being upfront about**: today, a visitor's info goes directly from their phone to the realtor's own inbox, with no intermediary ever seeing it. A form service means that data passes through a third party first — plus a new point of failure (an outage or a terms change breaks the feature for every realtor using it at once, unlike plain `mailto:`/`sms:` links, which depend on nothing staying online), and likely an ongoing cost depending on the service and submission volume, where today there is none.
  - Worth revisiting seriously if the lighter fix doesn't turn out to be enough once realtors are actually using it day to day — and if it does move forward, priced and positioned to reflect the real, recurring per-person setup and maintenance cost, not bundled into the standard realtor tier.

  - **Scope as discussed**: very simple, dogs and cats only for now, intake handled by text message rather than the full email intake form, no rework of any shared/load-bearing files at this stage. A future dedicated landing screen would swap "Get a Black Hat Card" for "Get a Black Collar Tag."
  - **Color palette**, pulled from a lost-pet flyer Boris shared: warm aged cream/parchment (`#EDE1C7`-ish) paired with a deep navy (`#1B2A47`-ish) — a distinct, warmer "vintage rescue flyer" look, deliberately different from the existing copper/black and navy/blue palettes used elsewhere in the project. Two mockups built from this (a pet card for Cookie, a landing-screen concept) — see this conversation for the actual visuals.
  - **Naming**: "Black Collar Tag" fits the existing family well — Black Hat Card, Black Hat Bracelet, Black Collar Tag reads as one coherent brand with a pet-specific variant, not a confusing departure.
  - **Real upside**: a genuinely different, large market (pet owners) with a strong emotional/safety purchase driver, untouched by anything else this project does.
  - **Real friction worth remembering before this becomes an actual build**: several of the existing card's always-on buttons (Refer a Friend, Collect Info, Scan a Card) exist for human networking and don't mean anything on a pet's card. They wouldn't break anything today, but they contradict the "very simple" goal if left as-is long-term — the one place "reuse the engine unchanged" and "very, very simple" are in real tension.
  - **Operational cost worth being honest about**: the single biggest constraint already logged elsewhere in this document is Boris's own manual intake pace. A second product line, even a simple, text-based one, adds to that same bottleneck rather than relieving it — worth going in clear-eyed about that trade-off, not just the upside.
- [ ] **Call / Text / Email / Web / Map icon row beneath the avatar photo — a design option, not an active plan.** Sparked by a reference screenshot Boris shared of a "Maya Lopez" realtor card showing a row of circular Call / Email / Web / Map icon buttons directly under the contact's photo, with the request to consider Call, Text, Email, Web Site, and/or address as the icon set (a slightly different list than the reference image's own Call/Email/Web/Map).
  - **The real appeal**: a single glanceable action row right under the face, before any scrolling — a different, faster interaction pattern than the existing contact section's tap-to-expand field rows further down the page.
  - **The core tension this would need to resolve**: it's largely redundant with what the card already does. Phone and email are already clickable fields in the existing Contact section (and, notably, phone already opens a Call-or-Text choice popup rather than dialing outright) — so an icon row would either duplicate that functionality in a second place on the page, or would need to fully replace the existing fields-based contact section rather than sit alongside it. Those are two very different builds, and nothing so far has settled which one this is.
  - **The multi-value complication**: the existing fields system already handles a person having more than one phone number or email address (rendered as separate rows, each independently tappable, each going through the same Call-or-Text popup for phone). A fixed-size icon row (one Call icon, one Email icon) doesn't have an obvious answer for "which number does the Call icon dial" when someone has two — this would need its own resolution (a picker on tap? first-listed-wins? icon row only appears when there's exactly one of each?) before it could be built generally, not just for single-phone/single-email cards.
  - **Address/Map is new territory**: nothing in the current engine renders a street address as a field today, so a Map icon would be the first address-aware feature in the person-card engine (property cards already handle addresses, but that's a separate engine/template). Would need its own data.json field and its own tap behavior (presumably a maps-app deep link) designed from scratch.
  - **Open questions to resolve before this goes beyond "an option"**: Does this row supplement the existing Contact section or replace it? What's the final icon set — the reference image's Call/Email/Web/Map, or Boris's stated Call/Text/Email/Web/Map/address wish list (six icons is a much more crowded row under a small avatar than four)? How does it behave for someone with multiple phones/emails? Is this universal (every card gets it) or a per-brand/per-tier design choice? Logged as a real reference point for a future design pass — not committed to, and no code changes made.
- [ ] **Pull the brand accent color(s) from the client's own existing card/logo image, when one is provided, instead of picking a color by eye.** Flagged while building the Shearin Auto & Diesel card — the brand's accent (`#D4AF37` gold) was chosen by looking at their physical business card photo and eyeballing a close match, the same manual approach used for every biz- brand built so far (Nelson's Pizza House red, Angel Wings Bookstore purple, etc.). Boris asked that the *next* card's design process actually sample color from the source image, rather than repeat the eyeball-and-guess step.
  - **What this would take**: when a client's existing card, logo, or flyer image is available, extract an actual hex value from it (e.g. sampling the dominant/brand-relevant pixel color from the uploaded image) rather than estimating by sight — then still run it through the existing `ensureContrast`-style check before it becomes `accent`/`accentSoft` in the brand's JSON, since a color sampled straight off a photo (lighting, JPEG compression, a busy background) won't always be readable against the site's near-black `--ink` without adjustment.
  - **Why this wasn't just done automatically already**: no tooling for this has been built or tried yet — today it's a human (Claude) visually comparing the image to a mental color reference and picking a plausible hex. A real sampling step would mean actually reading pixel values from the uploaded image file (e.g. via a quick script) rather than estimating from the rendered description of it.
  - **Likely still needs a judgment call on top of sampling**: a straight dominant-color or center-pixel sample can land on the wrong element entirely (e.g. picking up a black background or a photo behind the logo instead of the brand's actual signature color) — so this probably isn't a fully mechanical swap-in, more a better starting point before applying the same contrast/sanity check used today. Worth trying on the next biz card build with a reference image, not a backend project.
- [ ] **Tap/usage counting per card, with stats viewable by Boris first and cardholders later — CODE WRITTEN AND TESTED 2026-10-16 (in `tap-counter-build/`, see its `SETUP-TOMORROW.md`); remaining: connect the Redis store in Vercel, set the admin password, push the files.** Today, Vercel Web Analytics (already in every card's template) shows views over time per card path in the Vercel dashboard, visible only to Boris. It counts all page views (QR scans, shared links, refreshes, testing alike) and can't reliably tell a physical tag tap from a link click. This entry is the plan for a real, shareable per-card counter. Only taps over time are wanted for now; rough location (county) is a nice-to-have for later.
  - **Chosen approach — a beacon from the card page, NOT a redirect.** An earlier idea (a `/t/<card-id>` redirect logging each tap before forwarding) was set aside: it would require reprogramming every NFC tag already issued (they point straight at the card URL) and adds a hop to every tap. Instead, `assets/app.js` sends a small fire-and-forget "this card was opened" message to a serverless function on page load. Because it lives in the shared `assets/` file, every existing live card starts counting on deploy with no template changes and no tag reprogramming.
  - **What gets stored**: daily counters only — one Redis hash per card (`tap:<folder>`) with a field per day and source (`<YYYY-MM-DD>:tag` / `:link`), incremented by the function; days follow Eastern time. (This replaced an earlier one-key-per-day sketch because reading a card's whole history becomes a single lookup.) No IP addresses, no per-visit rows, no device info. Storage: a Redis store from Vercel's integrations (Upstash is the usual pick) — atomic increment, generous free tier; connected from the Vercel project dashboard, which auto-adds the connection settings.
  - **Noise filtering**: count once per browser session (sessionStorage) so refreshes don't inflate it; views carrying the `?t=` token count as "tag tap," views without it as "shared link/QR"; skip Boris's own views via a one-time flag set in his browser; link-preview bots don't run page JavaScript, so they're excluded naturally. Honest labeling: this counts opens of the page — a good proxy for taps, not a perfect NFC-tap count.
  - **Viewing the numbers, in two stages**: (1) **Boris only** — a `stats.html` admin page: pick a card, see taps per day/week/month, protected by a password set as a Vercel environment variable. Do this first; it needs no cardholder-access decisions. (2) **Cardholders later** — a private per-card stats link with its own key (same security class as the access token: link-based, fine for "how many taps did I get," not sensitive data), or a monthly summary Boris sends by hand. Real cardholder logins remain the separate, heavier authentication item already logged above.
  - **County/location later**: Vercel passes country, region, and city to serverless functions automatically; county is not included, so it would be an approximate mapping from city. Since the counter key is `card:date`, adding a place dimension later is a small change, not a rebuild. If ever added: store coarse place only, never the raw IP.
  - **Privacy**: with daily-totals-only, the impact is minimal, but `legal/privacy-policy.html` section 6 ("Cookies & Analytics") should gain one sentence saying card opens are counted as daily totals with no individual visitor information stored. If per-visit records or location are ever added, the policy/terms need a fuller update (what's recorded, retention window, who can see it), and a qualified reviewer is worth it if tracking becomes a paid feature. Not legal advice.
  - **Risks to plan for**: (a) first non-static piece of the project — adds an `api/` folder, a Vercel storage connection, and a vendor dependency; (b) the beacon MUST be fire-and-forget and kept out of `app.js`'s main render try-block — any exception there shows the "Couldn't load this contact's data" screen, so a counter outage must never be able to take cards down; (c) function invocations per page load are well within typical plan allowances but worth glancing at once real volume exists.
  - **Split of work for tomorrow**: Claude writes `api/tap`, `api/stats`, the `app.js` beacon, `stats.html`, and the policy line, and tests them with a mock store. Boris connects the Redis store in the Vercel project (a few clicks, walked through step by step) and sets the admin password env var.
- [x] **Website link as an on-page QR code (person cards) — BUILT AND TESTED 2026-10-29 (in `qr-links-build/`: `assets/app.js`, `assets/style.css`, `generator.html`); first used on a client's micro-site (Mo Tea link).** Triggered by a client request to have a link's QR code sit on the page like the "Scan" section, tappable and printable. Replaces a first popup-style design that read as messy.
  - **How it works**: in `data.json`, a `websites` entry can carry `"qr": true` (optional `"qrCaption"`, `"qrShowUrl": true`). Each such link gets its own block above the Scan section: heading = the link's label, the code (tap to open, scan to open), caption (default "Scan with your phone's camera, or tap the code to open the link."), and a "Print this QR code" link. Built entirely in `app.js`, so it reaches live cards with the shared files, no template change needed.
  - **Decisions made**: the plain label row always stays in the Contact box, and the label always heads the block. The web address text (e.g. moteajar.com) is hidden by default, shown only with `"qrShowUrl": true` ("Also show the web address" tick box in `generator.html`). An earlier `"qrOnly"` option (hid the Contact row) was dropped; the code ignores it, so any `"qrOnly": true` left in a `data.json` is harmless and can be deleted.
  - **Also done**: the "Scan" section code now matches the link code size (shared `style.css`, so property cards match too); fixed the old "Print QR Code Only" dark-border bug (white backing behind `#qrcode`, verified decodable on person and property cards).
  - **Known limits**: max 3 QR blocks per card; person cards only (property cards not built); long links make denser, harder-to-scan codes (prefer short links such as forms.gle/...); the intake form and message-to-json do not offer the QR options (generator.html or hand-editing `data.json` only); tap counter does not count taps on these codes; printouts verified with a decoder only, not yet with a real phone.
  - **Ideas not built**: property-card version; split the Contact-row hiding back out as its own option if a client ever wants only the code with no plain link row; add the options to the intake form.
